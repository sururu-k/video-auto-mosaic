# 検査キューを「連結」から「順位づけ」に変える（issue #21）2026-08-25

`docs/10` が実素材（マイビデオ-3、55,303フレーム）で報告した `review_frames 37,775件（68.3%）`
は、issue #21 が別素材で報告した「9,249件を連結すると動画の95.7%を指す」と同じ形の問題。
「怪しい場所を優先して見る」ための道具が、実質「全部見ろ」になっていた。

このPRは issue #21 の完了条件のうち「区間ベースへの再設計」（API 形状・フロント・判定記録
形式にまたがる、PR #63 が既に見送ると判断した部分）ではなく、**キューの中身と並び順**
（`automosaic/review.py` の `build_queue` 周り）だけを扱う。

`data/library/20260823-234604-9be9`（`docs/10` `docs/11` と同じジョブ。source.mp4 /
output.mp4 / det.json / report.json 一式。55,303フレーム、1920x1080、`--despike` 相当の
コードで焼かれている）と、`C:\Users\shieru_k\Downloads\video\pooblem.md`
（他社ツールの漏れを人間が確認した78区間）。

`pooblem.md` は `tools/parse_leak_report.py` で毎回そのソースから再パースし、
`data/bench3/leaks_reported.json`（先行セッションが作った同じ変換結果）と全78区間が
1件も違わないことを確認してから使った（RULES.md 2.1「先行の数字を見てから測って
合わせにいった」を避けるため、先に自分で測ってから突き合わせた）。

```
$ tools/parse_leak_report.py pooblem.md -o leaks_fresh.json --fps 30
78 区間 / 合計 701 秒 (11.7 分)
$ diff leaks_fresh.json data/bench3/leaks_reported.json  (frame単位で比較)
78/78 一致
```

## 何を「答え」とみなすか

`pooblem.md` の78区間のうち、**このジョブの `ReviewSession.coverage` が `COV_NONE`
（実観測も推定も一切無い＝素通し）と自己申告しているフレーム**を「確実に未塗装」と呼ぶ。
`docs/11` が同じ定義・同じジョブで独立に測った値（5,075フレーム）と、本PRの実装した
`ReviewSession` で測り直した値がフレーム数まで一致した（5,075）。これは以前の数字を
見てから合わせたのではなく、`docs/11` は画素そのもの（出力動画をデコードして構造を見る）
から出した数字で、本PRの測定は `ReviewSession.coverage`（検出+補間+memoryの計算結果、
画素は見ない）から出した数字。**別の経路で同じ数字に着地した。**

## 実測1: どの理由がこの5,075フレームを捕捉するか

`ReviewSession` を `--despike` 付きでこのジョブに対して組み、理由ごとに独立して
「その理由の区間が及ぶ範囲」と「確実に未塗装」の重なりを数えた。

```
despiked   区間  252件  未塗装  25/5075 捕捉  (0.5%)
estimated  区間 2334件  未塗装   0/5075 捕捉  (0.0%)
uncovered  区間  222件  未塗装 5075/5075 捕捉 (100.0%)
area_jump  フレーム 1050件  未塗装 0/5075 捕捉 (0.0%)
low_conf   フレーム36409件  未塗装 0/5075 捕捉 (0.0%)
```

**`estimated` は定義上ここを1件も捕捉できない**（「推定のみ」＝どこかに領域があるので
`coverage != COV_NONE`。素通しの集合とは論理的に交わらない）。`area_jump` `low_conf` は
交わりうるが、この素材では実測0件だった。

一方で `despiked` は `uncovered` に完全に埋め込まれない。捨てたトラックの帯に
**他対象の実観測が残っていて `coverage` が `COV_REAL` に見えるケース**（`uncovered`
では絶対に拾えない）が実在する:

```
78区間 ∩ despiked区間               100 フレーム
  うち uncovered では拾えていない     75 フレーム（他対象の被覆で隠れている）
```

これは `#23` / `PR #63` が指摘した「despike が捨てた帯は、他の根拠で被覆済みに見えると
検査キューに一度も出てこない」の実例が、この実素材の既知漏れ集合の中にも実在する
ということ。**despiked を最優先のまま残す根拠**になる。

## 優先度の入れ替え

以前の並びは despiked(1) > **estimated(2)** > uncovered(3) > area_jump(4) > low_conf(5)。
「推定のみ」を「未処理」より上に置いていたのは処理の重さ（推定はどこかに領域はあるが
位置が怪しい/未処理は実観測が皆無）という直感によるもので、実測した結果ではなかった。

上の実測（uncovered が100%、estimated が0%）に基づき、
**despiked(1) > uncovered(2) > estimated(3) > area_jump(4) > low_conf(5)** に入れ替えた。

## 実測2: 既定キューの件数と、既知漏れ78区間の捕捉率

既定のキュー（`all_frames=False`）を **despiked と uncovered の2理由だけ**に絞った
（`DEFAULT_QUEUE_REASONS`）。理由: 実測1で、この2理由だけで「確実に未塗装」5,075
フレームを100%捕捉できると分かった一方、`estimated`（2,334区間）`area_jump`（1,050件）
`low_conf`（36,409件、動画の66%相当）は実測0件の寄与で、既定キューの体積の大半を
占めていた。**削除ではなく降格**（`all_frames=True` で全理由に戻る。既に
`frontend/src/review/app.tsx` の `setAllFrames` がこの引数に配線済みなので、
フロントを一切変えずに「全部見る」導線が動く）。

さらに、1区間あたりの代表フレーム数に上限（既定3、`DEFAULT_MAX_PER_RANGE`）を設けた。
以前は `step`（既定5フレーム）刻みで区間の長さに関係なく拾っており、この素材の
最長未処理区間（644フレーム = 21.5秒）1本だけで129件のキュー項目を生んでいた。
始点・終点は必ず残す（区間の存在とおおよその範囲は伝わる）。

**実装した `automosaic.review.build_queue` / `ReviewSession` そのもので測定**
（`session_from_args` で実際にこのジョブを開いたときと同じ経路）:

```
既定キュー(despiked+uncovered, max_per_range=3, step=5)   846件
  理由別  despiked=248  uncovered=598

既知漏れ78区間の「確実に未塗装」5,075フレームに対する捕捉:  5075/5075 (100.0%)
捕捉できなかったフレーム: 0件・0.0秒

all_frames=True（全理由・全区間、フル）                  20,355件
  理由別  despiked=248 uncovered=598 estimated=3586
          area_jump=579 low_conf=6525 sampled=8819

846 / 20,355 = 4.2%（既定キューはフルの24分の1）
```

**捕捉できなかったものは無い（0件）。** ただし「捕捉」の定義は「その区間のどこかに
既定キューの代表フレームが1枚でも入っている」こと（`docs/11` と同じ、区間単位の粒度）で、
1区間内の特定の1フレームまで保証するものではない。区間そのものは
`max_per_range=3` で間引かれても始点・終点が残るため、消えることはない。

**`estimated` / `area_jump` / `low_conf` を既定から外したことによる新しいリスク**:
この3理由が捕捉していた「78区間データセットでは測れない種類の壊れ方」
（推定位置のズレ、面積の急変、低信頼の検出）は、既定キューからは見えなくなる。
78区間データセットは「他社ツールが完全に沈黙した場所」の集合であり、
「検出はしたが位置がズレている」「そのものは塗ったが別の場所にも漏れがある」を
測る物差しではない。**0%は「この物差しでは効かなかった」であって「無価値」ではない**
ため理由自体は消さず、`all_frames=True` で確実に見られる状態を残した。

## 件数の目標をどう決めたか

1件あたりの所要時間の見積もりは、issue #21 本文が例示していた「1件2秒」を使う
（判定ボタンをタップするだけの最速ケース。実際には「怪しいので直す」判定は
矩形を置く操作が要り、もっと長くかかる）。846件 × 2秒 = 1,692秒 ≈ **28分**。
「直す」判定が混ざる分を保守的に見て 5秒/件としても 846件 × 5秒 = 4,230秒 ≈ **71分**。

30分強の実素材に対して 28〜71分は、`docs/10` が測った旧来の 37,775件（同じ尺度なら
数時間〜12時間オーダー）と比べて桁が違う。**「作業の簡略化」を最優先にした結果として、
846件という数字は事後に付いてきたもので、先に846を目標にして絞ったのではない。**
先に決めたのは「despiked と uncovered の2理由だけを既定にする」という方針で、
846はその方針をこの実素材に当てた結果の実測値。動画の長さ・漏れの実数によって
他の素材では増減する。

`update_payload`/`ranges_payload` とは別のエンドポイント）を、このジョブで実測。

```

all=1（フル、比較用）                    20,355件 3,134,371B
```

**103,727B は #61 が基準にした 466KB を下回る。** `#61` が最適化した
`update_payload()` / `ranges_payload()` はこのPRで変更していない
（参考: 同ジョブの `ranges_payload()` は 140,175B、既定のまま不変）。

## 全部見る導線

`all_frames=True`（`ReviewSession.queue_all` / API の `all=1`）は元々あった
「全フレームを間隔ごとにキューへ載せる」機能で、このPRで意味を強化した:
以前は「候補に挙がった理由に加えてsampledで穴埋めする」だけだったが、
`estimated`/`area_jump`/`low_conf` を既定キューから外した今は、
**`all_frames=True` が「降格した理由も含めて全部見る」の入口を兼ねる。**
フロント（`frontend/src/review/app.tsx` の `setAllFrames`）は既にこの引数を
呼んでいるため、**フロントを一切変更せずに導線が機能する。**

`queue_payload()` にも `omitted_by_default`（既定キューから外れている理由と
その区間・フレーム数、`all_frames=True` なら空）を足した。フロントがまだ
この値を表示しなくても、往復のたびに「何が・何件外れているか」が payload に
残るため、黙って消えたことにはならない（RULES.md 0）。

  は本PRで扱っていない、**別の・独立した集計**。`docs/10` の「37,775件」はこの値で、
  `review.py` の `build_queue()` とは別の実装が別の基準（間引きなし・理由をまとめて
  素朴にフラグを立てる）で数えている。本PRの変更後、この2つの数字は一致しなくなる
  （`review_frames` は変更前と同じ計算のまま）。次に着手するなら、
  `review_flags()` 自体を `build_queue()` の理由分類・既定絞り込みに揃えるか、
  この統計自体を役目が終わったものとして扱うかを判断する必要がある
- 846件という具体的な数は **この1本の実素材でのみ実測した値**。動画が長くなる・
  漏れが多い素材では大きくなる。「846件」自体を目標値としてハードコードしていない
  （キューの中身は理由の集合とその区間で決まり、件数は結果でしかない）
- `min_cells` の校正（`docs/11` / PR #83）と同様、**この実素材で測った結果を
  そのまま他の素材に借りない**こと。別の実素材（`data/bench3` 等）で同じ測定を
  やり直すのが望ましいが、本PRでは時間の制約で1本にとどめた
