# 夜間の自律作業計画

作成 2026-08-23。利用者が就寝中に自律で進める作業の手順書。
各項目は「終わったか判定できる条件」を持たせてある。判断に迷う変更、後戻りが
効かない変更、素材を消す操作は行わない。

## 守ること

- **テストが通らない変更はコミットしない。** `tests/test_render.py` と
  `tests/test_review.py` の両方が通ることを毎回確認する
- **既定値を勝手に大きく変えない。** 変えるなら実測の根拠とセットで、README に理由を書く
- **素材・過去の出力を消さない。** 整理は `data/**/_old/` への移動で行う
- **push は毎回行う。** 朝に見られる状態にしておく
- 目視判定は当てにならないことが実証済み（見落としと誤検出の両方が出た）。
  **独立した2つ以上の判定が一致したものだけを確定**として扱い、食い違いは
  「要確認」として残す。1つの判断で他を覆さない

## 作業項目

### A. 30分素材のベンチマーク（最優先・時間がかかる）

素材 `C:\Users\shieru_k\Downloads\video\マイビデオ-3.mp4`（1920x1080 / 30fps / 55,303フレーム）。
他社ツールで処理した結果に対する**人間検証済みの漏れ一覧**が
`data/bench3/leaks_reported.md` にある（84区間、時刻と部位つき）。

1. 検出を回す（実行中: `data/bench3/det.json`）
2. 84区間を機械可読な形に変換する（`start_sec`, `end_sec`, `part`）
3. **各区間でうちの検出器が反応しているか**を集計する。ここが本題。
   他社ツールが漏らした箇所は「局部が確実に映っている」ことが保証されているので、
   うちがそこで沈黙していれば、それがうちの穴になる
4. 結果を `docs/03-benchmark-myvideo3.md` に書く。数字だけでなく、
   沈黙している区間の特徴（構図・動き・明るさ）を並べる

**終了条件**: 84区間それぞれについて「検出あり/なし」と最大スコアが表に出ていること。

### B. マイビデオ-5 の未検査区間を潰す

現状 1768 フレーム中 193 フレームしか目視していない。漏れは 35 箇所見つかっている。

1. 現在の出力 `data/myvideo5/v9.mp4` からフレームを抜く（未検査の区間、5フレーム刻み）
2. 目視検査のサブエージェントを並列で回す（1体あたり20〜25枚）
3. 結果を `data/myvideo5/leakcheck/` に保存し、`tools/leaks_to_annotations.py` で変換
4. `tools/annotations_to_corrections.py` で展開して焼き直す
5. **同じ区間を別のエージェントにもう一度見せ、判定が一致するか確認する**

**注意**: 543〜606 は、乳首と亀頭を取り違えた判定に基づく結果を破棄したので未検査扱い。
利用者が「亀頭」と確定させているので、この区間は漏れとして扱う。

**終了条件**: 全区間を最低1回検査し、漏れが見つかった区間は2回目の検査も済んでいること。

### C. 出力側の独立検証ゲート（未実装の設計項目）

設計上いちばん重要と位置づけながら未着手。

出力動画に対して、**本番で使っていない検出器**を走らせ、局部が検出されたら警告する。
入力側でどれだけ頑張っても保証にならないので、これが唯一の客観的な出荷条件になる。

- 本番は `weights/640m.onnx`。検証には `weights/320n.onnx` を使う（別の重み）
- モザイク済み領域でも検出器は反応しうるので、**検出位置が既存のモザイク領域の
  外にある場合だけ**警告する
- `tools/verify_output.py` として作り、`--report` に結果を出す
- マイビデオ-5 の v9 で試し、目視検査で見つかった 35 箇所とどれだけ一致するかを測る。
  一致率が低ければゲートとして使えないので、その事実を書く

**終了条件**: ツールが動き、目視検査の結果との一致率が数字で出ていること。

### D. 手修正から学習データを作る

`--export-dataset` は実装済み。実際に書き出して中身を確認する。

- マイビデオ-5 の修正から書き出す
- 画像とラベルの座標が合っているか、実際に矩形を描いた確認画像を数枚作る
- ファインチューンの手順を `docs/04-finetune.md` に書く（実行はしない。
  環境に torch が無く、AMD では現実的でないため。手順だけ残す）

**終了条件**: データセットが書き出され、座標の正しさが確認画像で示されていること。

### E. レビューUIの詰め

利用者が実際に触るので、明らかな不具合だけ直す。大きな作り替えはしない。

- 実際に HTTP で叩いて、判定→次のフレーム→取り消しの往復が壊れていないか
- キューが 364 枚と多い。低信頼（255枚）の優先度が高すぎないか見直す
- 起動が失敗する条件（ポート使用中、ファイルが無い）で分かるメッセージが出るか

**終了条件**: 往復が動くことを HTTP で確認済み。

## 進め方

優先度は A > B > C > D > E。A は検出待ちの時間があるので、待つあいだに B を進める。
1周ごとに `docs/05-overnight-log.md` に「何をして何が分かったか」を追記する。
朝に読めば経緯が追える状態にしておく。
