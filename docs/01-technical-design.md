# 実写動画 自動モザイク — 技術設計メモ

調査日: 2026-08-22
対象: 実写動画のみ

**設計軸: 1フレームの検出漏れ＝法的に致命的。**
過剰に潰すのは許容、漏らすのは不可。この非対称性をすべての判断の基準にする（Recall優先・Precision妥協）。

---

## 0. 処理方式の大前提

### ガウシアンブラーを使ってはいけない

- ブラーはデコンボリューションで復元可能
- モザイクですら DeepMosaics のような除去モデルが公開されている
- FLMASK事件・2021年京都府警の事案が示すとおり、**復元容易性は法的リスクの中核**

→ **ブロック平均色ピクセライズ**（各ブロックを平均色1色に量子化し、情報量を実際に落とす）か塗り潰しを選ぶ。

### モザイクブロックサイズ

法令に数値基準は存在しない。参照可能な唯一の公開数値は FANZA同人 第6条:
- 最小 4px四方
- 長辺400px以上なら「長辺 × 1/100」程度

これは同人・静止画向けであり、実写動画を規律するものではない。**下限の下限**として扱い、実装上は対象領域の実サイズに連動させる。

## 1. 推奨アーキテクチャ

検出器が主系。伝播とトラッカーは穴埋め専用。

```
デコード
  ↓
[A] 毎フレーム検出器（YOLO-seg、低しきい値 conf=0.10〜0.15）
  ↓
[B] トラッカー（ByteTrack / BoT-SORT）でID付与
  ↓
[C] 欠損フレームの穴埋め（3系統のOR合成）
      C1: frame memory（過去Nフレームの領域を無条件に残す）
      C2: カルマン予測による外挿
      C3: 前後の検出フレーム間の線形/スプライン補間（オフラインなので未来も使える）
  ↓
[D] マスク精緻化: SAM2 をショット内で伝播（オプション）
  ↓
[E] 膨張 + フェザリング + 時間平滑化
  ↓
[F] モザイク合成 → エンコード
```

**[A]の低しきい値が最重要。** ByteTrack の核心はまさに「低スコア検出ボックスを捨てずにトラックレットとの類似度で救済する」ことで、オクルージョン下の対象を回復し軌跡の断片化を減らす（MOT17でMOTA 80.3 / IDF1 77.3、V100 30FPS）。この性質が本用途の要件と完全に一致する。

### 2パス構成にすること

Zenn記事の設計を踏襲:
- **パス1**: 全フレーム検出、**座標だけをJSONに保存**
- **パス2**: 動画を読み直してモザイク描画

長尺でのメモリ問題と、中間フレームのディスク占有（1080p 1時間で数十〜百GB級）の両方を回避できる。DeepMosaics が全フレームをディスク展開しているのは真似しない。

## 2. SAM2 の位置づけ — 主系にはできない

| 項目 | 内容 |
|---|---|
| 速度 | Hiera-B+ **43.8 FPS**、Hiera-L **30.2 FPS**（A100、batch=1） |
| 破綻モード1: 誤り蓄積 | 一度誤ったマスクがメモリに入ると**訂正不能**で、以降のフレームを誤らせ続ける |
| 破綻モード2: 位置ドリフト | 空間特徴依存のため高速移動でドリフト・マスク断片化 |
| 破綻モード3: 長尺 | 数百フレームを超えるとメモリバッファがロールオーバーし、類似オブジェクトへ乗り移る |
| 対策研究 | SAM2Long（学習不要のメモリツリーで複数仮説を保持）、SAM2Plus（カルマンフィルタ統合） |

**「1点プロンプト→60分伝播」は成立しない。** 用途を次の2つに限定する:

1. **短ショット単位の伝播**（シーンカット検出で分割し、ショット内でのみ伝播。境界で必ずリセット）
2. **半自動アノテーション**（第5節）

## 3. 穴埋めと安定化

### 3-1. 手法

| 手法 | 実装例・備考 |
|---|---|
| frame memory | DashcamCleaner: 「現フレームの検出ボックスだけでなく、**過去nフレームで検出された領域も併せてぼかす**」。計算コストほぼゼロでfalse negativeを潰せる。**最初に入れるべき機構** |
| 未来方向の補間 | オフラインバッチなので `t-k` と `t+k` の両方に検出があれば `t` は必ず埋める。検出漏れが単発〜数フレームなら理論上ゼロにできる |
| カルマン + EMA + gap filling | Roboflow Detections Stabilizer が同じ設計思想で既製ブロック化されている |
| 信頼度のヒステリシス | 高しきい値（0.5）で「開始」、低しきい値（0.10）で「継続」。一度モザイクを始めたら簡単には切らない。Canny のヒステリシス閾値と同発想 |

### 3-2. 膨張(dilation)マージン

既存ツールの実績値:

| ツール | パラメータ | 値 |
|---|---|---|
| deface | `--mask-scale` | **1.3** |
| deface | `--thresh` | **0.2**（通常の物体検出より大幅に低い） |
| DashcamCleaner | ROI enlargement | 0.8〜10 で可変 |

設計指針（実測でなく出発点）:

```
margin_px = base + motion_term + confidence_term + jpeg_term

base            = max(0.20 * sqrt(mask_area), 12px)   # 面積依存の基礎マージン
motion_term     = 1.5 * (このIDの直近Nフレームの最大変位 px/frame)
confidence_term = (1 - conf) * base * 2               # 低信頼ほど厚く盛る
jpeg_term       = 8px                                 # 圧縮アーティファクトの染み出し対策
```

**フェザリングは「保証範囲の外側」に置く。** 先に `margin_px + feather_radius` まで膨張させ、その外周 `feather_radius` 分だけをグラデーションにする。逆順にすると保証範囲の端が半透明になり局部が透ける。

### 3-3. チラつき対策

| 症状 | 対策 |
|---|---|
| ボックスがフレーム間で跳ねる | EMAで座標を平滑化。ただし**平滑化は面積を縮める方向に働かせない** — 平滑化後に必ず `union(平滑化結果, 生検出)` を取る |
| モザイクが1フレームだけ消える | frame memory + 双方向補間で構造的に排除 |
| ブロックの格子位置が毎フレーム動く | グリッド原点を**フレーム座標に固定**する（bbox基準にしない）。`pixelize` はフレーム原点基準なので自然にこうなる |
| モザイクサイズが毎フレーム変わる | ブロックサイズをショット単位で固定、またはトラックID単位で移動中央値を取る |
| マスク境界が呼吸する | マスクを時間方向にも膨張（`t-2..t+2` のOR）してから空間膨張 |

## 4. ffmpeg でのモザイク適用

### 4-1. 手法比較

| 手法 | 評価 |
|---|---|
| A. 毎フレームのマスクPNG + `alphamerge` + `overlay` | フレーム単位の任意形状マスクを扱える唯一の純ffmpeg解。中間ファイルが大量。VFR素材で対応が崩れる |
| B. `maskedmerge` | 3入力。全入力のピクセルフォーマット・サイズを揃える必要があり、YUVでの取り回しが面倒。Aのほうが素直 |
| C. `sendcmd` / `zmq` で座標を動かす | **本用途には非推奨**。矩形1個ずつしか動かせず、領域数がフィルタグラフ構築時に固定。108,000行のコマンドファイルになる |
| D. Python(OpenCV)で全デコード→書き戻し | OpenCVの`VideoWriter`は**音声を落とし、色空間・CRFの制御が貧弱**。不可 |
| **E. Python で合成 → rawvideo を ffmpeg に pipe** | **本命**。Dの柔軟性とAの品質制御を両立、中間ファイルゼロ |

### 4-2. 手法E の具体形

デコード（YUVのまま取り出してRGB往復による色劣化を避ける）:

```bash
ffmpeg -i in.mp4 -f rawvideo -pix_fmt yuv420p -
# 10bit ソースなら -pix_fmt yuv420p10le
```

エンコード:

```bash
ffmpeg -y \
  -f rawvideo -pix_fmt yuv420p -s 1920x1080 -r 30000/1001 -i - \
  -i in.mp4 \
  -map 0:v \
  -map 1:a? -map 1:s? -map 1:t? \
  -map_metadata 1 -map_chapters 1 \
  -c:v libx264 -crf 16 -preset slow -pix_fmt yuv420p \
  -color_primaries bt709 -color_trc bt709 -colorspace bt709 -color_range tv \
  -c:a copy -c:s copy \
  -movflags +faststart \
  out.mp4
```

ポイント:
- **元ファイルを2番目の入力として再度渡す**。音声・字幕・チャプタ・添付・メタデータをそこから `-c copy` で持ってくる。これが「音声劣化ゼロ・字幕保持」の最も確実な方法
- rawvideo経由では色空間タグが失われる。`ffprobe -show_streams` で元の `color_primaries` / `color_transfer` / `color_space` / `color_range` を読み、**そのまま明示再指定**する。指定しないとBT.709と誤認されて色がずれる
- モザイクは **Y/U/V平面上で直接**かける。4:2:0の彩度平面は解像度が半分なのでブロックサイズを平面ごとに `//2`。RGB変換を挟むと8bit往復で微小な色劣化が入る

品質設定:

| 設定 | 値 | 根拠 |
|---|---|---|
| CRF | **16〜18**（既定23） | CRF 17〜18 が visually lossless とされる。CRF +6 でビットレート約半分 |
| preset | `slow`〜`slower` | 同品質でファイルサイズ減 |
| pix_fmt | **元と同じ** | 8bit→10bit化はバンディング低減に有効だがファイル増 |
| コンテナ | 元がMKVならMKV維持 | MP4は複数字幕・添付・一部コーデックを落とす |

上級手法: モザイク領域を含むGOPだけ再エンコードし残りはstream copyする「部分再エンコード」。実装コストは高いが、モザイク対象が一部にしか出ない素材では画質・時間の両方で大きく有利。GOP境界の特定に `ffprobe -show_frames -skip_frame nokey`。

未検証: HDR (PQ/HLG) 素材でのメタデータ完全保持。`maskedmerge` にグレースケールマスクをYUVで渡した際の彩度平面の挙動。

## 5. モデル選択

### 5-1. アプローチ比較

| アプローチ | マスク精度 | 適性 | 評価 |
|---|---|---|---|
| 物体検出（YOLO11/26, RT-DETR） | bboxのみ | 中 | 必ず矩形なので周囲を過剰に潰す。「過剰は許容」なので**最終フォールバック**としては有効。速い |
| **インスタンスセグメンテーション（YOLO-seg）** | ポリゴン（粗め） | **本命** | マスク解像度は160×160プロトタイプで粗いが、膨張前提なら十分。速度も実用域 |
| Mask R-CNN | 高精度だが遅い | 低 | YOLO-segとの速度差が大きく、精度差が膨張マージンに埋もれる |
| SAM2 refinement | 極めて高精度 | 併用 | 検出器のbbox/点をプロンプトに境界を精緻化。単独では対象を「見つけられない」（クラス概念を持たない） |
| 人体パーツセグメンテーション（SCHP / Sapiens） | 高精度だが**局部クラスがない** | 補助のみ | Sapiensの28クラスは髪・舌・歯・上下唇・胴体など**着衣人体前提** |
| **DensePose** | UV密対応 | **冗長系として有効** | 体表UV座標から「胴体パーツの特定UV領域＝股間」という**解剖学的事前分布**を作れる。検出器が完全に失敗しても人体さえ取れれば領域を推定できる |

**結論: YOLO11/26-seg を主系、DensePose（またはポーズ推定）を独立した第2系統、bbox全面塗りを最終フォールバックの3段構え。**

### 5-3. スループット（60分尺）

**出典のある単フレーム推論時間からの単純計算。実測値ではない。前処理・後処理・デコード・エンコード・トラッキングを含まない。**

60分 @ 30fps = 108,000フレーム。

YOLO26-seg（COCO、imgsz=640、T4 TensorRT10）:

| モデル | mAPmask | T4 TRT10 | CPU ONNX | 60分@30fps 推論のみ |
|---|---|---|---|---|
| YOLO26n-seg | 33.9 | 2.1ms | 53.3ms | 約3.8分 |
| YOLO26s-seg | 40.0 | 3.3ms | 118.4ms | 約5.9分 |
| YOLO26m-seg | 44.1 | 6.7ms | 328.2ms | 約12.1分 |
| YOLO26l-seg | 45.5 | 8.0ms | 387.0ms | 約14.4分 |
| YOLO26x-seg | 47.0 | 16.4ms | 787.0ms | 約29.5分 |

SAM2（A100、batch=1）: Hiera-B+ 43.8FPS → 約41分 / Hiera-L 30.2FPS → 約60分

**解像度依存性の注意:**
- YOLO-segは入力をimgsz(640/832)にリサイズするため、**1080pでも4Kでも推論コストはほぼ同じ**。変わるのはデコードと前処理
- ただし4Kを640に縮めると小さい対象がサブピクセル化して消える → **4KではSAHIタイリング必須**。640×640タイル、overlap 0.2 で4Kを覆うと重なり込みで30前後 → **推論コストが20〜30倍**
- imgsz 640→832 は FLOPs 約1.69倍

**現実的な全体スループット**: 上表の**2〜4倍**を見込むのが安全。4K 60分はSAHI込みで数時間〜十数時間オーダー。**バッチ処理・夜間実行前提の設計にすべき。**

コンシューマGPU（RTX 4090等）の信頼できる一次ソースは確認できず。自環境での実測が必要。

**自前構築が前提。**

### 6-2. ブートストラップ前提の工数

DeepMosaics の公式ドキュメントが必要量を示している:
- 必要枚数「**1000枚以上**」
- 推奨ワークフロー「**まず小さいデータで addmosaic モデルを学習し、それを使って大きいデータのデータセットを自動生成する**」

見積もり（実測でなく設計上の目安）:

| 段階 | 枚数 | 手法 | 目安 |
|---|---|---|---|
| Seed | 300〜500 | 完全手動ポリゴン | 1枚60〜120秒 → **6〜17時間** |
| 拡張1 | 3,000〜5,000 | Seedモデルで推論 → 誤りのみ修正 | 1枚10〜20秒 → **10〜28時間** |
| 拡張2 | 20,000+ | SAM2動画伝播で自動生成 → スポットチェック | 手作業は激減 |

**多様性の確保が枚数より重要。** 同一動画から1000フレーム抜いても実質1シーンぶんの情報しかない。**動画1本あたり20〜50フレーム**を上限に層化サンプリング。特に意図的に集めるべきもの:
- 動きが速くブレているフレーム（**検出漏れの最大要因**）
- 部分オクルージョン（手・衣類・体位）
- 極端な逆光・暗所
- 対象が画面の1%未満の小さいフレーム

### 6-3. SAM による半自動アノテーション

1. シーンカット検出でショット分割（ffmpeg `select='gt(scene,0.3)'` / PySceneDetect）
2. 各ショットの代表フレームに人手で1〜2点プロンプト
3. SAM2でショット内伝播
4. サンプリング目視（10フレームに1枚など）、破綻箇所で再プロンプト
5. 承認されたマスクをデータセットに投入

**CVAT の SAM2 Tracker** がこれをそのまま実装している。Nuclio版はEnterprise限定だが、AI Agent版はユーザー側エージェントで動くためCVAT Onlineでも使える。GPUデプロイ推奨。

### 6-4. 著作権法30条の4（断定を避けた整理・法的助言ではない）

| 論点 | 整理 |
|---|---|
| 基本構造 | 「著作物に表現された思想又は感情を自ら享受し又は他人に享受させることを目的としない場合」に原則許諾なく利用できる。AI学習のための情報解析は**非享受目的**に該当し原則適法とされる |
| ただし書 | 「著作権者の利益を**不当に害することとなる場合**」は適用外 |
| 例外: 表現出力目的 | 学習データと同一・類似の出力を意図的に生成する目的が併存する場合は適用外 |
| 侵害抑止措置 | 侵害物の生成を抑止する技術的手段を講じていることは非享受目的の推認要素 |

本件への当てはめ（整理であって結論ではない）:
- 本ツールは**識別モデルであって生成モデルではない**。学習データと類似した映像を生成する能力を持たない。表現出力目的の併存は考えにくく、30条の4が比較的当てはまりやすい類型に見える
- ただし**訓練用に動画を入手する行為そのもの**は別問題。海賊版と知りながらのダウンロードは30条の4以前の問題。**適法に入手した素材のみを使う**
- 学習後の**データセットの外部公開・配布**は30条の4の射程を超える可能性が高い。**社内に閉じること**
- **弁護士確認を取るべき論点**。著作権法だけでなく175条・AV新法・肖像権が絡む

### 6-5. 児童ポルノ規制法 — 絶対条件

「学術研究目的なら単純所持罪に当たらない」とする解説はあるが、**これに依拠した設計をしてはならない**。

- 「研究目的」は本人の主観であり、**捜査段階で信用される保証がない**
- 製造罪・提供罪は構成要件が異なる
- **年齢は映像から判定できない**。18歳と17歳を見た目で区別することは不可能

**運用ルール（例外なく守る）:**

1. **年齢確認済みの素材のみ**を使う。国内の正規流通品（審査団体を通ったもの）、またはAV出演被害防止・救済法に基づく契約・年齢確認記録が確認できる素材に限定
2. **Webスクレイピングを一切行わない**。無作為収集した素材の年齢を保証する手段が存在しない。**最大の禁止事項**
3. **素材の入手元・年齢確認の根拠を1本ごとに台帳化**。購入証跡・出演者年齢確認の所在を記録
4. **自己制作素材（自分または成人の同意者を撮影）が最も安全**。数百枚のseedなら現実的に自作可能
5. 学習済みモデルは公開しても、**データセットは絶対に外に出さない**
6. 疑わしい素材が1本でも混入したと分かった時点で、**その素材由来のフレームを全削除し、モデルを再学習**
7. **実写のみ**を扱う（二次元・イラストは対象外と割り切る）
8. **保管場所を暗号化しアクセスを限定**。研究目的であっても第三者が閲覧可能な状態は「提供」に該当しうる

## 7. フェイルセーフ設計

### 7-1. 信頼度レイヤ

```
レイヤ1（高信頼）: conf >= 0.5 かつトラック安定
    → 通常モザイク（マスク形状 + 標準マージン）

レイヤ2（中信頼）: 0.1 <= conf < 0.5、またはトラック補間で埋めたフレーム
    → 拡大モザイク（マージン2倍）+ レビューキューにフラグ

レイヤ3（低信頼 / 未検出だが人体は存在）
    → bbox全面 or 人体下半身の解剖学的推定領域を全面モザイク + レビュー必須

レイヤ4（人体すら検出できない / デコードエラー / シーン全体が異常）
    → フレーム全面モザイク or 処理中断
```

**原則: 「判断できない ＝ 潰す」。判断できないから何もしない、は絶対にやらない。**

### 7-2. 自動アラート条件

| 条件 | 理由 |
|---|---|
| トラックの中断（Nフレーム以上検出なし→再出現） | 中断区間に漏れがあった可能性 |
| 検出信頼度が閾値付近で振動 | モデルが迷っている＝データ分布外 |
| マスク面積がフレーム間で2倍以上／半分以下に急変 | 誤検出または部分検出 |
| マスクがフレーム端に接している | 見切れによる部分検出の可能性 |
| モーションブラー指標（ラプラシアン分散）が閾値以下 | 検出漏れの最大要因 |
| 輝度が極端（暗所・白飛び） | 同上 |
| シーンカット直後の数フレーム | トラッカーが立ち上がっていない |
| マスクが画面の0.1%未満 | 小さすぎて見落とす領域 |
| **検出器Aと検出器B（DensePose推定）の不一致** | **アンサンブル不一致は最強のアラート信号** |

### 7-3. 二重系（アンサンブル）

異なる失敗モードを持つ2系統を走らせ、**ORで合成**する（ANDではない — ORがRecall優先）:

- 系統A: YOLO-seg（局部を直接検出）
- 系統B: 人体検出 + ポーズ/DensePoseから解剖学的に推定した領域

Aが失敗してもBが人体さえ取れれば領域が出る。両者の不一致は必ずレビューへ。過剰に潰れるのは許容という要件があるのでORのコストは低い。

### 7-4. 人手レビューUI

**基本思想: レビュー担当者は全フレーム（108,000）を見られない。UIの仕事はレビュー対象を1/1000に絞ること。**

| 機能 | 設計 |
|---|---|
| タイムライン | 全長を横軸に信頼度をヒートマップ表示。赤＝レイヤ3以下。**赤いところだけ見ればよい**状態にする |
| フリップブック表示 | フラグ区間を「モザイク前/後」の2枚並べて**グリッド一覧**（1画面16フレーム）。1フレームずつ再生させない |
| モザイク前画像の扱い | **原画をそのまま見せない**。「マスク境界の外周だけを原画で見せ、内側は潰したまま」の差分ビュー。労務上も重要 |
| 修正操作 | ブラシで領域を**追加するのみ**。削るのはワンクリックで可能にしない（誤って漏らす操作を作らない）。削除は確認ダイアログ+理由記録 |
| 区間一括操作 | 「このトラックIDの t1〜t2 を全部拡大」がワンアクション。フレーム単位の作業を強制しない |
| キーボード駆動 | `J/K` 次/前フラグ、`Space` 承認、`X` 要修正 |
| 監査ログ | 誰がどのフレームを承認/修正したかを全記録。**「注意義務を尽くした」証跡**になる |
| 最終ゲート | 全フラグが承認/修正済になるまで**出力ファイルを生成させない** |
| **出力後の検証パス** | 生成済み出力に**学習に使っていない別モデル**で再スキャンし、露出が検出されたらアラート。検出されたら出荷しない |

**最終検証パスが実質的に最も重要。** 入力側でどれだけ頑張っても保証にならない。「出力に対して独立の検出器を走らせ、何も検出されないこと」を出荷条件にするのが唯一の客観的なゲート。

## 8. 実装順序

**ツールは非配布（自己使用のみ）で確定しているため、AGPL/GPL の重み・コードをそのまま使える。**
自前アノテーション（段階4、10〜45時間）は既製重みで精度が足りないと判明してから着手すればよく、初手に置かない。

| 段階 | 内容 | 判断ポイント |
|---|---|---|
| 0 | 素材の適法性の確保（年齢確認済み素材の入手ルート確定）、弁護士への論点整理相談 | ここが通らなければ以降は無意味 |
| 1 | EraX-NSFW + NudeNet(640m) でbboxベースラインを作り、手法E（Python合成 + rawvideo pipe）で全面bboxモザイクを実現。**音声・字幕・色空間の保持を先に完成させる** | 「とにかく漏らさない版」がまず動く |
| 2 | ByteTrack + frame memory + 双方向補間を追加。検出漏れフレームを実測してカウント | 補間で漏れがゼロになるか |
| 3 | 既製の YOLO11-seg 重みでマスク化し、過剰潰しを削減。ここまで自前学習ゼロ | bbox→マスクで見栄えが実用域に入るか |
| 4 | 精度不足が実測で確認できた場合のみ、seed 300〜500枚を手動アノテーション → ファインチューン → SAM2半自動（CVAT）で5,000〜20,000枚に拡張 | どのケースで落ちているかを段階2の実測で特定してから着手 |
| 5 | 二重系（DensePose系統）とレビューUI、出力側再スキャンゲートを実装 | 出荷可否の客観ゲートが立つ |
