# モザイク生成の質の批評 2026-08-23

`docs/07-audit-2026-08-23.md` が扱ったのは全部「壊れ方」（黙って素通しを作るバグ、
クラッシュ、競合）。これは**生成ロジックそのもの**の批評。

実測はすべて `data/bench3/det.json`（実素材 1920x1080 / 55,303f、frame_step=5）と
`data/bench3/clips/src_*.mp4`（実素材フルHD 2クリップ）。

---

## 構造的に漏れる場面

### S1 「被覆」が、矩形が対象の上にあるかを一度も見ていない（最重要）

`temporal.py` の `covered = sum(1 for f in range(n_frames) if out[f])` も、
`docs/03-benchmark-myvideo3.md` の被覆率も、**そのフレームに矩形が1個でもあるか**
しか見ていない。矩形が対象の上にあるかは判定に入っていない。

人間が「確実に映っている」と確定した78区間（20,718フレーム）での実測:

| 設定 | 区間内フレーム被覆 | うち実観測(detected)由来あり | 位置が推定のみ |
|---|---|---|---|
| 既定 | 66.6% | 6.7% | 被覆の 89.9% |
| `--estimate-gaps` | 83.5% | 6.7% | 被覆の 92.0% |
| 最大(mem20/bridge300) | 95.4% | 6.7% | 被覆の 93.0% |

docs/03 の数字は再現できた。だが**「95.4%塞げた」の中身は93%が位置の推測**。
この区間内で実際に推論した 4,206枚のうち対象クラスが1つでも出たのは
**1,470枚 = 35.0%**。

docs/03 の「うちの検出器が反応した区間 77件 (99%)」は区間単位の指標で、
**フレーム単位の recall は 35%**。この2つの数字が同じ文書に並んでいて、
後者は書かれていない。

### S2 補間と memory 外挿が、往復運動で対象を完全に外す

`densify()` は観測間を線形補間し、memory 区間は端点速度で等速外挿する。
どちらも「対象は直進する」前提。この道具の対象は直進しない。

合成実測（対象サイズは実素材の検出矩形 sqrt(面積) 中央値 191px に合わせた。
正弦運動、1080p、既定マージン）:

| 条件 | 平均被覆 | 完全被覆 | 対象が100%モザイクの外 |
|---|---|---|---|
| 振幅120px/周期24f、補間ギャップ12f | 83.8% | 2/10 | 0/10 |
| 振幅120px/周期24f、補間ギャップ30f | 72.5% | 10/28 | 0/28 |
| 振幅250px/周期20f、補間ギャップ12f | 45.6% | 1/10 | 1/10 |
| 振幅250px/周期20f、補間ギャップ90f | 53.1% | 19/88 | 12/88 |
| 振幅250px/周期20f、`--memory 20` 外挿 | 40.6% | 7/20 | **11/20** |
| 振幅120px/周期12f、`--memory 20` 外挿 | 71.2% | 6/20 | 0/20 |

**`--memory 20` の外挿区間は 20フレーム中11フレームで対象が矩形の完全に外に出る。**
等速外挿は往復運動では符号を間違えるので「固定するより悪い」領域がある。
`temporal.py` のコメントは「memory 区間は矩形を固定してはいけない。対象が動いていると
置いていかれる」と書くが、往復運動では**外挿のほうが置いていかれる**。

平均被覆 83.8% を成功と読んではいけない。矩形の16%が縁からはみ出しているというのは、
その部位が出ているということ。

実データでの規模: 補間ギャップは 3,631箇所、中央値5f、p90 30f、
**30フレーム(1秒)超が306箇所で合計16,874フレームを直線で埋めている**。
最大90fは `stitch_max_gap=90` で頭打ちになっているだけで真の分布は切られている。

### S3 `bridge_uncovered` がフレーム単位でしか動かない

`covered = [bool(per_frame.get(f)) for f in range(n_frames)]` ——
**フレームに矩形が1個でもあれば「覆われている」**。対象Aが塗られていれば、
対象Bのトラックが死んでいても bridge は起動しない。同じ欠陥が
`estimated_only_ranges` の `has_real = any(...)` にもあるので、レビュー報告からも消える。

実測（重複排除済み）:

- 同一対象と見なせる（stitch と同じ IoU/距離/サイズ比の条件を満たす）トラック対の間で、
  その対象が一切覆われていないフレーム: **41,331枚**
- うち他対象の矩形があるため bridge が起動しないもの: **25,995枚（62.9%）**
- うち人間が「確実に映っている」と確定した区間の中: **14,382枚**

素材の漏れ一覧は「上人物男性器」「下人物男性器」「左人物」と書かれていて、
2人以上が同時に映る素材。同時検出2件以上は間引きサンプルの6%だが、それは
**両方検出できているときの数字**で、片方が落ちている場面こそが問題の場面。

### S4 デスパイクが「唯一の証拠」を消している

`if len(t) < cfg.min_track_len and t.max_score < cfg.despike_conf` ——
1フレームだけの検出はスコア0.35未満なら捨てる。`--conf 0.06` まで下げておきながら、
`docs/04-finetune.md` が「実素材でのスコア中央値は 0.15 前後」と書いている。
**真陽性の大半が「単発なら捨てる」帯に入っている。**

実測: 破棄トラック319本のうち、**確実に映っている区間内の実観測を125件捨てている。
うち40件は、そのフレームに他に何も塗られておらず、捨てた結果そのフレームが素通しになった。**

誤検出のコストは塗り過ぎ＝許容なのだから、捨てる理由がない。既定であるべき根拠が
docs のどこにもない。

### S5 正方レターボックスが入力テンソルの44%を黒帯に捨てている

`detector.py` の `side = max(wh, ww); square = np.zeros((side, side, 3))`。
16:9 素材だと正方の下 43.75% が黒。ところが `weights/640m.onnx` の入力は実測で
`['batch', 3, 'height', 'width']` で**完全に動的**。

`segmenter.py` は既に非正方入力の経路を実装していて、そのコメントに
「素材が 4:3 なら正方に詰めると 25% が黒帯になって実効解像度を捨てることになる」と
自分で書いてある。**同じことを detector.py でやっていない。**

実測（実素材1080p 110枚、DirectML）:

| 入力 | テンソル画素 | 対象クラスが出たフレーム | 平均最大score | 推論 |
|---|---|---|---|---|
| A 正方960（現行既定） | 921,600（44%が黒帯） | 40/110 (36.4%) | 0.044 | 275ms |
| B 1280x736（比維持） | 942,080（2%が黒帯） | **52/110 (47.3%)** | **0.070** | 334ms |
| C 正方1280（現行方式で解像度up） | 1,638,400 | 51/110 (46.4%) | 0.066 | 497ms |

**B は C と同等の検出を 33%短い時間で出す。** A比では検出フレーム +30%、
平均最大score +59%、時間 +21%。

加えて `cli.py` の `detect_scale = args.infer_size * max(1, args.tiles)` により、
パス1は 1080p 素材を長辺960にデコードしてから検出器に渡す。縮小と黒帯埋めが二重。

### S6 クラス定義が175条の対象を覆いきっていない

`detector.py` の LABELS は NudeNet の18クラス。**陰嚢のクラスは存在しない。**
`DEFAULT_CLASSES` は EXPOSED 3種のみ。

漏れ一覧の内訳: 男性器59件、**陰嚢9件/42秒**、陰茎3件、肛門1件、
**「肛門異物挿入時の断続的なモザイク外れ」1件/74秒**（78区間中で最長）。

docs/03 の唯一の完全沈黙（7:41、0/60フレーム）はまさに陰嚢。
挿入部・器具・結合部は NudeNet の学習分布に「露出した性器」として存在しない可能性が高い
（モデルがそれでも発火するかは未検証）。

`--classes conservative` で COVERED を足せるが既定では落ちる。「隠れている性器」は
挿入・遮蔽の場面そのもので、既定から外す理由が説明されていない。

### S7 `--margin-cap 16` が他の7つのパラメータを死なせている

実測（既定設定、53,558領域）: **静的マージンが `--margin-cap 16` で切られた領域は 77.5%。**

つまり `margin_scale`(0.35)、`base_ratio`(0.15)、`base_min/max`(6/40)、
`score_reference`(0.5)、`confidence_weight`(0.5)、`estimated_factor`(1.3)、
`margin_cap_ratio`(0.5) は、8割のケースで出力に一切影響しない。README の膨張マージンの
説明（4項の和）は、実際には `min(..., 16) + motion` にしかなっていない。

合計マージンは既定で中央値40px・最大76px、最大設定でも中央値89px・最大124px。
一方、実素材の局所速度 p90 = 11.4px/frame なので `max_gap=12` ぶんの移動は 137px。
**マージンの上限が、トラックが許容するギャップぶんの移動量に届いていない。**

（この速度は5フレーム間引きの観測差分なので、往復運動はエイリアシングで過小に出ている。
中央値3.4 / p90 11.4 / p99 26.1 / 最大 68.3 px/frame。`motion_cap=60` を超えるのは
0.0% だが、これも間引きの効果。）

### S8 実害を確認できなかったもの

- `drop_area_ratio` の全面 drop —— 接写で発火すれば最悪だが、この素材では **0件**
- `_infer` の `argmax` —— YOLOv8 のクラススコアは多ラベルなので argmax が
  「対象クラス0.3、FACE 0.4」のアンカーを捨てるはず、と読んだが、実測（実素材220枚
  7,076アンカー）では**抑制されたアンカーは1件のみ、多ラベル化で救えるフレームは0**。
  この重みでは実質ほぼ one-hot に出ている。仮説は外れ
- `stitch_dist_ratio=0.12` = 1080p で 264px の誤結合 —— 実データでは特定できなかった（未検証）

### S9 segmenter.py は完成しているのに一度も呼ばれない

`grep -rn "Segmenter" automosaic/ tools/` は `segmenter.py` 自身以外に**参照ゼロ**。
`weights/nsfw-seg-penis-s.onnx` と `nsfw-seg-vagina-s.onnx` は置いてある。
README は「セグメンテーションによるマスク化」を未実装リストに入れているが、
**推論器は書けている。使っていないだけ。**

マスク化そのものは塗り過ぎ削減の施策であって漏れ対策ではない（docs/06 が
「bbox が漏れてマスクが漏れないことは原理上ない」と正しく書いている）。
価値は**学習データが別（NSFW-API の YOLO11-seg）の第二の意見**という点にある。

### S10 render のブロック格子

`_snap` はフレーム座標の格子にスナップする。チラつき対策としては正しい。ただし
対象が固定格子の下を動くと、同じ部位が異なるサブブロック位相で何度も標本化される
（多フレーム統合による復元の材料）。ブロックサイズ 長辺/100 の根拠は FANZA同人の
**静止画向け**基準で、`render.py` 自身が「実写動画を規律するものではない。下限の下限
として扱うこと」と書きながら既定に採用している。

実測の根拠が docs にあるもの: `--infer-size 960`（ただし640x480素材1本での測定）、
`--conf 0.06`、memory を固定でなく外挿にした判断（ただし往復運動では逆効果）、
`--estimate-gaps` 既定 off、`--device-id 1`。

値だけで根拠が無いもの:

| パラメータ | 値 | 状況 |
|---|---|---|
| `--nms-iou` | 0.45 | docs に一切言及なし。YOLO の既定値そのまま。唯一の参照情報（docs/00「NMS 0.25 が良好との報告」）と食い違う |

| `--motion-weight` | 2.0 | 由来なし。設計案は 1.5 |
| `--memory` / `--memory-before` | 6 / 0 | 6 も、絞り込み後の 2 も根拠なし |
| `--hold-growth` | 0.5（コード既定は0.25で不一致） | README 本文に説明が一切ない |
| `--bridge-max` | 150 | 根拠なし。README は「3秒以内」と書くが 150f@30fps = 5秒で数字が合わない |

## 評価方法の穴

docs/03 の評価は「他社ツールが漏らした78区間で、うちの検出器が1回でも反応するか」。

1. **GT が座標を持たない。** 「時刻区間＋部位名」だけ。したがって「検出はしたが矩形が
   対象の70%しか覆っていない」型の漏れは**原理的に測れない**。同文書が自分で
   「見つかった漏れ52件のうち半分以上がこの型だった」と書いている。
   **過半数を占める漏れの型を、主要ベンチマークが測っていない。**
2. **サンプルが他社ツールの弱点で層化されている。** 他社が正しく塗れた箇所
   （動画の62%の時間）でのうちの性能は完全に未測定。誤検出率・Precision も未測定。
3. **判定粒度が「区間内で1回でも」。** 同文書の表自身が 6/90、8/60、11/120 を並べている。
   **1秒60フレームのうち6フレームだけ反応しても「検出できた」と数えている。**
4. **「漏れ0」と出ても実際は漏れている構成**: (a) 1区間に2対象があり片方だけ検出
   （S3 の 14,382フレーム）、(b) 検出したが矩形が対象の70%しか覆わない（S2）、
   (c) 弱い検出が despike で消えたが区間内の別フレームで拾えた（S4 の40フレーム）
5. **`tools/verify_output.py` は出荷ゲートとして機能しない。**
   `--model` の既定が `weights/640m.onnx` で**本番の既定と同じ重み**、`--infer-size` も
   既定 960 で本番と同じ。違うのは `--conf 0.10` で、これは本番の 0.06 より**厳しい**。
   つまり既定実行は本番の検出結果の部分集合しか出せない。**構造的にほぼ必ず0件で通る。**
   `--min-outside` 既定 0.5 —— **検出矩形の49%がモザイクの外でも報告しない。**
   docs/05 が別モデルとして使った `320n.onnx` も同じ NudeNet の同じ学習データの別サイズ版。
6. **README の「（未実装）」の意味。** 実態は「実装して失敗が確定している」（docs/05）。
   docs/05 が自分で「隠さず README にも書く」と決めているのに反映されていない。
   **未実装であることの意味は、この道具に出荷判定が存在しないということ。**
7. 1本の動画・1人の評価者・1系統の素材（myvideo-5 と myvideo-3 の2本のみ）

## 175条対応として通用するか

**通用しない。** 現状は「人手で全編チェックする作業を速くする道具」であって、
無人で焼ける道具ではない。README が自分でそう書いており、その記述が正しい。

- 対象が確実に映っている場面での**フレーム単位 recall は 35%**
- 残り65%は補間と外挿の推測で埋めており、その推測は往復運動で最大 20フレーム中11フレーム
  完全に外す
- 対象単位の穴 25,995フレームが bridge からもレポートからも見えない
- 出荷判定が無い。既定の `verify_output.py` は本番と同じ検出器の厳しい版なので必ず通る
- 陰嚢（42秒）と挿入（74秒）は検出器のクラス定義に存在しない

**そして「何%の確度か」は、現在の評価系では原理的に答えられない。** 答えるには
(a) 座標つきGT、(b) 画素単位の被覆指標、(c) 学習データが独立した第二の検出器
の3つが要り、**3つとも無い**。

## 改善提案（優先順）

### P0 評価指標を「矩形の有無」から「画素被覆」に変える

コスト小（1〜2日）／効果 決定的。これをやらないと以降の改善が測れない。

- GT を「時刻区間」から「矩形つきフレーム」に。種は既にある:
  `data/myvideo5/dataset`（384枚、YOLO形式）と `data/myvideo5/corrections.json`
- 指標を「GT矩形のうち塗られた画素の割合」と「被覆が100%未満のフレーム数」に。
  `verify_output.py` の `_covered_fraction` がそのまま使える
- あわせて `--min-outside 0.5` を 0.05 程度に下げる

### P1 正方レターボックスをやめる

コスト小（半日）／効果 実測で検出フレーム +30%、score +59%。

`detector.py` の正方詰めを `segmenter.py` の非正方経路に置き換える。ONNX は既に動的入力。
あわせて `cli.py` のデコードサイズを「長辺 infer_size」でなく「ネット入力の画素予算に
合わせた比維持サイズ」に。**この項目だけ、コストがほぼゼロで効果が実測済み。**

### P2 bridge と estimated_only_ranges を対象単位にする

コスト中（2〜3日）／効果 実測25,995フレームが対象。

`covered[]` をフレーム単位の bool から「トラック系統ごとの被覆」に変える。
`stitch_tracks` が既に「同一対象らしさ」の判定基準（IoU / 中心距離 / サイズ比）を
持っているので、それを `stitch_max_gap` の外側にも適用して系統を作り、系統ごとに
穴を埋める・報告する。同じ修正が `estimated_only_ranges` にも要る。
**現状はレビュー報告からも消えているので、人手チェックの導線にすら乗らない。**

### P3 デスパイクを既定で切る

コスト極小（1行）／効果 実測40フレームの素通しを直接解消。

誤検出のコストは塗り過ぎ＝許容という設計原則と整合させるだけ。捨てるにしても
「捨てた場所をレポートに出す」に変えれば、原則の「判断できない区間は黙って素通ししない」
を守れる。

### P4 推定区間のマージンを「速度の外挿」でなく「不確かさの包絡」にする

コスト小（1日）／効果 「完全に外した」を 0 に。

等速外挿は往復運動では符号を間違えて**誤差を倍にする**。代わりに:

- memory 区間は矩形を外挿せず、「直前の観測位置 ± 局所速度 × hold」を**両方向**に
  膨らませた包絡矩形にする。塗り過ぎ側に外れる
- 補間区間も同様に、両端の観測の外接矩形に `speed × hold` を全方向に足す

あわせて `--margin-cap 16` の既定を見直す。マージンの根拠を1つも実測していない現状で、
上限だけが効いているのは最悪の組み合わせ。

### P5 二系統目として segmenter を併走させる

コスト中（2〜3日）／効果 大。**学習コスト0で今日試せる唯一の選択肢。**

重みは置いてあり、`segmenter.py` は完成していて、cli.py から一度も呼ばれていない。
