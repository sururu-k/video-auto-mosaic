# 画素被覆ツールの実装と実測 2026-08-24（issue #7）

`docs/11-coverage-vs-leak-report.md` が一度きりの分析として実測した「モザイクの
構造そのものを見る基準」を、`tools/pixel_coverage.py` として再利用可能な形にした。
GT を「時刻区間」でなく「矩形つきフレーム」（`corrections.json` の `add` 項目、
または `data/myvideo5/dataset` の YOLO ラベル）に対して使えるようにしてある。

## docs/11 の数字をそのまま信じなかった

`RULES.md` 2.1「既知の基準を借りてこない」の通り、docs/11 の校正値
（20px グリッド、`std_min=6.0`、`ratio_max=0.35`）を実際にこの素材
（`data/myvideo5/マイビデオ-5.mp4` 640x480、`v11.mp4`）に適用したところ、
**そのままでは全く使い物にならなかった**。

1. `render.default_block_size(640) == 6` を信じて `--cell 6` で測ったところ、
   GT 433件の平均被覆率が **21.2%**、100%被覆 0件という異常値が出た。
2. `v11.mp4` の実際の出力画素を run-length で数え直したところ、
   **実際に焼かれたブロックは 12px**（`default_block_size` の理論値と不一致）。
   これは呼び出し側の記録が無い以上、コードの式では分からない。
3. `--cell 12` に直しても `std_min=6.0`（docs/11 の 1080p 校正値）のままだと
   平均被覆率 **45.8%**、測定可能面積（後述）**51.1%** と、まだ多くのセルが
   「元がもともと平坦で判定不能」として除外されていた。
4. `--std-min 2.0` まで下げ、視覚的にオーバーレイ画像で確認（フレーム100、577、
   900、1300 の4枚）してようやく、実際に見えるモザイク領域を過不足なく
   拾えていることを確認した（誤検出0、モザイク領域の内部がほぼ塗り潰される）。

**教訓は docs/11 が書いた通りだった。閾値は借りてこず、毎回その素材で測り直す
必要がある。** そこでツール側に2つの対策を入れた。

- `--cell` 省略時は `render.default_block_size` の理論値に頼らず、
  出力動画の GT フレームから実際のブロック境界を run-length で実測する
  （`detect_block_size` / `detect_block_size_over_frames`）。理論値が実測と
  一致する保証は無いので、実測できなければ警告した上で理論値にフォールバックする。
- 評価結果に `measurable_fraction`（GT box のうち判定可能な面積の割合）を出す。
  これが低ければ `std_min` がこの素材には高すぎることの直接的なシグナルになる。

## 実測（`v11.mp4` / `corrections.json` の add 433件・427フレーム）

```
$ PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe tools/pixel_coverage.py ^
    --source data/myvideo5/マイビデオ-5.mp4 --output data/myvideo5/v11.mp4 ^
    --corrections data/myvideo5/corrections.json ^
    --std-min 2.0 --ratio-max 0.35 --min-cells 2

ブロックサイズを出力動画の5フレームから実測: 12px
診断格子セルサイズ 12px  std_min=2.0  ratio_max=0.35  min_cells=2

GT 433 件（427 フレーム）

[旧指標] フレームに矩形/塗りが存在するか（有無のみ）
  433 / 433 (100.0%)

[新指標] GT矩形のうち実際に画素で塗られている割合
  平均被覆率            62.5%
  100%被覆              0 / 433 (0.0%)
  被覆が100%未満        433 件
  完全に塗られていない  33 件
  平均測定可能面積      73.5%
```

**旧指標は100%、新指標は平均62.5%。** 旧指標（フレームに矩形/塗りが存在するか）
は`v11.mp4`の全GTフレームで「何かしら塗られている」ことしか見ていない。実際に
GT矩形の場所を見ると、平均でその62.5%しか画素として潰れておらず、**433件全部が
100%未満、33件は完全に0%（対象の位置に一切モザイクが無い）。**

frame 577（同フレームに GT box が2件: `[495, 240, 80, 90]` と
`[510.8, 261.2, 45.2, 47.2]`）を出荷する既定（`--cell` 省略時の自動実測 12px、
`--std-min 2.0`）で測ると:

```
{'frame': 577, 'box': [495.0, 240.0, 80.0, 90.0], 'pixel_coverage': 0.5975,
 'measurable_fraction': 0.6275, 'pixel_coverage_among_measurable': 0.9522}
{'frame': 577, 'box': [510.8, 261.2, 45.2, 47.2], 'pixel_coverage': 0.7293,
 'measurable_fraction': 0.7293, 'pixel_coverage_among_measurable': 1.0}
```

同じ2つの box を、この節の冒頭で「使い物にならない」と判定した設定
（`--cell 6 --std-min 6.0`、640x480素材に対して理論値 `default_block_size(640)==6`
をそのまま信じた設定）で測ると `pixel_coverage` は `0.115` / `0.234` になる
（**5倍近く低く出る**。この差自体が、cell を誤ると被覆率が実際より低く出る
方向に振れることを示している。旧指標側ではなく box 指標側の話であることに
注意）。

両方の box の範囲を出力動画から切り出して目視すると、12px 格子のモザイク
ブロックのパターンが範囲全体に明瞭に確認でき、測定可能な範囲内ではほぼ
塗り潰されている（測定可能面積内の被覆 95.2% / 100%）。これは出荷する既定の
数値（59.75% / 72.93%）と整合し、`--cell 6 --std-min 6.0` の数値（11.5% /
23.4%）とは整合しない。**この2つの box が「対象の上にほとんどモザイクが
無い」例だという記述は誤りで、出荷する既定・目視のどちらでも支持されない。
訂正する。**

このフレームは「大部分が塗られている」例であって「漏れの代表例」ではない。
GT 433件全体では33件が測定可能範囲内でも完全に0%（対象の位置に一切モザイクが
無い）のまま残っており、漏れの実例はそちらで確認できる（`corrections.json`
の note にある「シルエット縁の亀頭が露出」等）。**旧指標（フレームに矩形/塗りが
存在するか）はこれら33件も含めて全433件を「モザイクあり」としか報告できない。**
対象の上に乗っているかを一度も見ていない、というのが issue #7 の核心であり、
この点は frame 577 に頼らずとも 33/433 の完全未塗装で示せる。

未確認: `corrections.json`（生成 2026-08-23 11:47）は `v11.mp4`（生成
2026-08-23 03:46）より後に作られている。タイムスタンプから、`corrections.json`
の `add` 項目は「`v11.mp4` が見逃した場所」として後から人間が足したものである
可能性が高いが、これは推測であり、`v11.mp4` の生成コマンド自体は確認していない。
そうだとすれば、GT 側が意図的に「旧パイプラインが漏らした場所」に偏っている
ことになるので、**この62.5%という数字は「一般的な被覆率」ではなく「既知の
弱点における被覆率」として読むこと。**

## `tools/pixel_coverage.py` の使い方

```
.venv/Scripts/python.exe tools/pixel_coverage.py \
  --source 元動画.mp4 --output 出力動画.mp4 \
  --corrections corrections.json \        # または --yolo-dataset dataset/
  [--cell N]                              # 省略時は出力動画から実測
  [--std-min 6.0] [--ratio-max 0.35] [--min-cells 2] \
  [--calibrate]                           # 閾値を決める前の分布測定
  [--report out.json]
```

**`--calibrate` は今回のような分布の分離を確認するためのものだが、この素材
では「フレームに何か塗られているか」自体があまり分離しない**（GTフレームも
非GTフレームも中央値が近い）。理由は、この動画がほぼ全編にわたって連続した
対象を含み、`min_cells` ベースのフレーム単位判定では「そのフレームのどこかに
モザイクがあるか」がほぼ常に真になるため。**これはツールの欠陥ではなく、
まさに issue #7 が指摘している「有無」指標の限界そのもの。** 実際に意味のある
判定は box 単位の `pixel_coverage` の方であり、`--calibrate` は閾値そのものの
妥当性（誤検出が出ていないか）を個別フレームのオーバーレイ目視で確認する
補助として使うこと（本ドキュメントのフレーム100/577/900/1300の確認がそれ）。

## `detect_block_size` は1920x1080の実素材で外れる。しかも警告なしだった

640x480 素材では実測が理論値の誤りを正しく検出できたが、別の実素材
（1920x1080、真のブロックサイズ 20px の完成品）で実測すると逆に外れた。

```
$ 元動画 data/library/20260823-234604-9be9/output.mp4 (1920x1080) を
  -ss 300/600/900/1200 の各点で5フレームずつ detect_block_size に通す

-ss 300 : [20, 20, 4, 4, 4]  中央値 4
-ss 600 : [4, 4, 4, 4, 4]    中央値 4
-ss 900 : [4, 4, 4, 4, 4]    中央値 4
-ss 1200: [20, 20, 20, 20, 4] 中央値 20
モザイク無しコントロール(source.mp4を同区間で実測): [4, 4, 4, 4, 4] 中央値 4
```

4点中3点で中央値が真のブロックサイズ(20)ではなく4になり、**警告を出さず
「実測: 4px」と表示していた。** この cell=4 で未塗装コントロール692フレーム
相当を評価すると、旧指標(`frame_is_painted`)が1080pで692フレーム中692フレーム
（=検証した全フレーム）を誤って「塗装あり」と判定する（詳細は次節）。原因は
自然な肌・布のテクスチャや圧縮ノイズが 4px 間隔のエッジを大量に作り、
`min_gap=4` の下限にほぼ確実に張り付くこと。docstring が書いていた
「モザイクが無いフレームを渡すと検出できない（None を返す）」も誤りで、
実際には None を一度も返さず自信満々に 4px を返し続けた。

これを受けて次の2つを実装した（`detect_block_size` 自体のロジックは変えて
いない。周期性を使った再検出ロジックを試したが、この素材のノイズと弱い
モザイク信号を安定して分離できず、かえって危険な誤検出を増やしかねないため
採用しなかった。RULES.md 2.1「毎回、自分の素材で分布を測ってから閾値を決める」
の通り、閾値だけを変えて「直った」と主張しない）。

- **実測値が `render.default_block_size(width)` の理論値と食い違うときに警告する。**
  上の4点全てで発火する（4点とも理論値20pxと不一致）。
- **サンプルフレーム間で実測値が割れたときに警告する。** `-ss 300` と
  `-ss 1200` で発火する（`-ss 600` `-ss 900` は5点とも4に揃っており、割れの
  警告だけでは検出できないが、理論値との食い違い警告は4点とも発火する）。

```
$ 出荷する既定(--cell 省略)で myvideo5(640x480)を評価
警告: 実測ブロックサイズ 12px が理論値 default_block_size=6px と一致しません。
どちらか一方が誤っている可能性がある（640x480素材では理論値が誤りだったが、
1920x1080素材では実測が4px に外れ理論値20pxが正しかった実例がある）。
--cell で明示指定するか、目視で確認すること。
ブロックサイズを出力動画の5フレームから実測: 12px（フレームごと: [12, 12, 12, 12, 12]）
```

640x480 素材では理論値(6px)ではなく実測(12px)が正しく、1920x1080素材では
逆に理論値(20px)が正しく実測(4px)が外れる。**どちらを信用すべきかは cell の
値だけからは判定できない**（本ドキュメント冒頭の教訓通り）。だから自動選択は
せず、食い違いを常に警告して人間の目視判断に委ねる形にした。

## 旧指標・`--calibrate`・box 指標は cell の誤りに対して同じ強さで壊れない

**旧指標（`old_existence_covered` / `frame_is_painted`）と `--calibrate` は、
`cell` が実際のブロックサイズと一致しているときだけ意味を持つ。cell を外すと
「素通し側」に誤る。** box 単位の `pixel_coverage` は cell を外しても「塗り
過ぎ側」に留まる。この2つの違いは指標の作りそのものに由来するので、両方を
同列に扱わないこと。

**実測（`data/library/20260823-234604-9be9/source.mp4` の1080p 10秒区間を
libx264 crf16 で無加工のまま再エンコードしたもの＝実際に検出0件だった場合の
出力を模した「未塗装コントロール」、これを実際のブロックサイズ20pxではなく
`detect_block_size` が実測で外した4px で評価）:**

```
[旧指標] 誤って painted 判定: 10/10
[新指標] box coverage (誤検出) n=300 mean=0.0308% max=0.4800% p99=0.2804%
```

`frame_is_painted` はフレーム全体に「潰れたセル」が `min_cells`（既定2）以上
あるかしか見ない。cell を小さくしすぎると、圧縮ノイズや自然なテクスチャが
生む偽の「潰れたセル」がフレーム全体のどこかに `min_cells` 個見つかる確率が
急激に上がる（1920x1080 を 4px 格子で見ると 129,600 セルある）。この実測では
**未塗装10フレーム全部を「モザイクあり」と誤判定した。** `--calibrate` は
この `frame_is_painted` 相当の分布を見る機能なので、同じ壊れ方をする。

box 単位の `pixel_coverage`（`box_mask_fraction`）は、GT box というローカルな
範囲内の潰れたセルの**割合**を見る。cell を誤っても偽の潰れたセルはフレーム
全体に薄く散らばるだけなので、1つの box の中に占める割合は小さいまま
（実測: 平均0.03%、最大0.48%、p99 0.28%）。**「塗られている」と誤って強く
主張することはない。**

まとめると、`--cell` を外したときの壊れ方向は指標ごとに違う。

| 指標 | cell を誤ったときの壊れ方 |
|---|---|
| 旧指標（矩形/塗りの有無） | 素通し側（実測: 未塗装フレームを100%「塗装あり」と誤判定） |
| `--calibrate`（`frame_is_painted` の分布） | 同上。閾値の分離判断ごと信用できなくなる |
| box 指標（`pixel_coverage`） | 塗り過ぎ側には振れない（実測: 誤検出は平均0.03%/最大0.48%に留まる） |

`--cell` を省略したときの自動実測（`detect_block_size`）にどこまで頼れるかは
別問題（本ドキュメント冒頭と `detect_block_size` のdocstring参照）。実測が
外れても box 指標の結論（塗られているかどうか）はさほど動かないが、
旧指標と `--calibrate` の結論は cell の実測が外れた瞬間に信用できなくなる。

## `--min-outside` の既定を下げた

`tools/verify_output.py` の `--min-outside` を **0.5 → 0.05** に変更した。
旧既定では検出矩形の49%がモザイクの外でも漏れとして報告しなかった
（`docs/09` S8 参照、当時の実測）。この変更自体は再検証していない
（`verify_output.py` は元動画への再検出を要し、GPU 推論が必要なため今回は
実行していない。**未実行。**）が、コード変更としては値の変更のみで副作用は無い。

## メモリ: 必要フレームを辞書に溜めていた

`collect_needed_frames` は必要フレーム全部を `{frame: (元, 出力)}` の辞書に
溜めてから処理していた。1920x1080 の gray 平面は1枚 2,073,600 バイト、
元+出力の2枚を21,030フレーム分溜めると 2,073,600 x 2 x 21,030 ≒ 87GB になる
計算で、GT が多い動画では動かない。`evaluate()` を `iter_needed_frame_pairs`
（1枚読んだら評価してすぐ手放すジェネレータ）を使う形に直し、辞書に全部を
保持しないようにした。`collect_needed_frames` 自体は `--cell` の自動実測用の
サンプル5枚取得など、必要フレーム数が少ない用途に限定して残してある
（docstringに明記）。myvideo5 (433件・427フレーム、704件・384フレーム) の
両方で変更前と数値が完全一致することを確認済み（本ドキュメントの実測値）。

## まだ測れていないこと

`docs/11` が書いた「原理的に測れない」ものは、この productionize でも変わらず
測れていない。

- **2人以上映る場面でどちらが塗られたか。** GT box が「誰の」対象かをクラス名
  以外で区別する情報を持たないので、同じフレームに複数の同クラス GT がある
  場合、どちらの mosaic 領域がどちらの GT に対応するかは見ていない
  （box 単位の重なりだけを見るので、対応関係を間違えても数字は変わらない）。
- **誤検出率・precision。** 今回は「見逃し」側の GT だけを見ており、
  過剰塗り（over-mosaic）の測定はスコープ外のまま。
- `measurable_fraction` が低い box（元がもともと平坦）は、被覆率を
  過小評価している可能性がある。今回の実測では平均73.5%が測定可能だったが、
  残り26.5%は「判定不能」であって「未塗装」ではない。
